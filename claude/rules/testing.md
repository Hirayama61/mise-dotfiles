# コンポーネントと関数のテストの規約

テストの構造と命名はリポジトリのテスト規約に従う。無ければ `describe` に状況、`it` に外から観測できる結果を書く。
レビューで当てる観点の全文は `~/.claude/skills/frontend-review/references/test.md` にある (`T-xx`)。

## 置き場所

- 2 か所以上で使う関数・部品には自身のテストを置く。場合分けの表 (`describe.each`) はその関数のテストに書き、呼び出し元には結果が入ることを確かめる 1 件だけ残す。
- テストは振る舞いを持つ部品のファイルに置く。親のテストに子の振る舞いを書かない。
- ある部品の操作の結果が別の部品に表れる流れは、両方を組み合わせる親のテストに通しの流れとして書く。

## 粒度

- 1 操作 1 `it`。初期表示と操作後を同じ `it` で見ない。
- 起こりえない状態 (押せないボタンを押す) をテストしない。
- 実装の都合 (見つからない値を既定値に畳む) を正しい振る舞いとして固めない。実装を直す対象にする。

## 確かめる振る舞い

実装で増えた分岐と操作を列挙し、それぞれを `expect` しているテストがあるかを確かめる。次は必ず入れる。

- 応答を待っている間 (押せない、閉じない、二重に呼ばれない)。応答待ちは、解決を後から呼び出せる Promise を使う。
- 失敗したあと (留まる、入力が残る、もう一度できる)。
- 複数の API を呼ぶときの応答の順番。
- `disabled` などの守りを外すとそのテストが落ちること。
- 開く対象ごとの初期値を Root を描画して確かめること。

## テストデータとモック

- リポジトリの factory とテスト用 utils を使う。テストファイルの中で書き直さない。
- 同じ補助関数が 2 ファイル以上にあれば共有へ出す。

## Story

- 新しく作った部品と props を変えた部品には Story を置く (Storybook のあるリポジトリ)。
- 見た目だけの部品は表示が変わる props の組み合わせ (0 件・上限の境目・長い名前・未入力・送信中) を出す。
- store や API につなぐ部品は、MSW で主要な操作を通しで見せる Story を 1 つ置く。
