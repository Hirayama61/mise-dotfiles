# frontend-review

レビューの結論と修正計画は主セッションが出す。
観点を当てて候補を集めるのはサブエージェント、MUST の反証は `refuter` に出す。
観点は `references/` の 3 ファイル。各項目に ID・兆候・決まり・直し方の形・重さ・対象外がある。

| 観点   | ファイル                   | ID   | 見るもの                                                                 |
| ------ | -------------------------- | ---- | ------------------------------------------------------------------------ |
| 分け方 | `references/structure.md`  | S-xx | 部品の層・props の形・純粋関数化・置き場所・型の出どころ・分岐の置き方   |
| 書き方 | `references/expression.md` | E-xx | 説明変数・定数・型の派生と判別 union・hooks の使い方・CSS とマークアップ |
| テスト | `references/test.md`       | T-xx | テストの置き場所・粒度・確かめていない振る舞い・モック・Story            |

重さは MUST (直さないとマージしない)・SHOULD (直してほしいが別コミットでもよい)・NITS (好み)。
範囲は「この PR で直す」か「別チケット可」。この差分で触ったファイルは、差分の外の行も「この PR で直す」。触っていないファイルへ波及する直し方は、形を書いたうえで「別チケット可」にする。

## 1. 対象を決める

引数が無ければローカル差分。base は現ブランチの PR の base、PR が無ければ既定ブランチ。
差分は merge-base からワークツリーまで (`git diff $(git merge-base origin/<base> HEAD)`)。
未追跡の新規ファイルは `git diff` に出ないので、含めたいなら先に `git add -N` を頼む。
PR 番号なら `gh pr diff`、ファイルパスならそのファイル。

対象は変更された `.ts` / `.tsx`。分け方と書き方はテストと Story を除き、テストはテスト・Story・実装ファイルを対象にする。
対象と base を 1〜2 行で伝える。

## 2. 3 観点を並列に出す

`general-purpose` のサブエージェント 3 つを 1 回の応答で同時に起動する。1 観点 1 エージェント。レビューは新しいコンテキストで行わせ、主セッションの推測を渡さない。
各エージェントに次を渡す。

- 対象ファイルの一覧と差分の取り方。
- 観点ファイルの絶対パス (`~/.claude/skills/frontend-review/references/<観点>.md`)。最初に Read し、ID の順にすべて当てること。
- 変更したファイルは全体を読み、差分は「どこを変えたか」の確認にだけ使うこと。import 先の同じ機能のフォルダも読むこと。
- ファイルを書き換えないこと。
- 「2 か所以上で使う」「素通りしている」「同じ定数がある」は `git grep` で数え、数えられなければ「未確認」と書くこと。
- 直し方を当てたとき、いまの動き (表示・取得の回数・エラー時) が変わるなら「動きが変わる: 〜」と書くこと。
- 出力の形 (下記)。

テストのエージェントには、分け方の結果を待たずにいまのコードで T-01〜T-07 を当てさせる。T-08 は主セッションが分け方の結果を受けてから、テストのエージェントに `SendMessage` で structure の結果を渡して足させる。

エージェントの出力の形は次のとおり。

```text
## <path>
### [MUST|SHOULD|NITS] <ID> <一言>
- 範囲: この PR で直す | 別チケット可 (<理由>)
- 根拠: <path:line> と、確かめたこと (`git grep` の件数、expect の有無)
- 直し方: <diff か、型・props・シグネチャ・木を含むコードブロック。移すならファイルの移動先>

## 出さなかった理由
<観点に当てはまるが出さなかったもの。理由は「リポジトリの規約と矛盾する」か「未確認で根拠が足りない」のどちらか>
```

分け方のエージェントには、指摘の前に「目標の木」(1 行 1 ファイル。新規 / 移す / 変える / そのまま と、知っていてよいこと) を書かせる。
指摘がないファイルは `## <path>` の下に「なし」。NITS は 1 ファイル 3 件まで。

## 3. 検証する

- MUST の指摘は 1 件ずつ `refuter` に出す。渡すのは指摘の本文 (ID・根拠・直し方) と対象ファイル。「反証できず」のものだけ残す。
- SHOULD は主セッションが根拠の `path:line` を開いて確かめる。
- 「未確認」が付いた指摘は、主セッションが数えて確定させるか、SHOULD 以下に落とす。
- 「動きが変わる」が付いた直し方は、修正計画に入れず「論点」として報告に残す。

## 4. 1 つにまとめて報告する

1. 目標の木 (分け方の結果をそのまま)。
2. 指摘の一覧。ファイルごとに MUST → SHOULD → NITS の順。`path:line`・ID・範囲・直し方を落とさない。
   書き方と分け方が同じ箇所を指すときは両方を残して「同じ箇所」と添える。
   2 つが同じファイルの形やシグネチャで食い違うとき (引数の数・props の形) は分け方の形を採り、書き方の diff は移った後のコードに当て直す。
3. 修正計画。3 観点の計画を 1 本にする。順は 型の export → 置き場所の移動 → 純粋関数 → hook → Root と枠 → parts → 呼び出し側 → 書き方の diff → テスト → Story。各手順に対象ファイルと ID を書く。1 手順 1 コミットにできる粒度。
4. 反証で落とした指摘と、出さなかった理由 (3 観点分をまとめる)。
5. 論点 (動きが変わる直し方、範囲の判断が分かれるもの)。

最後に「この修正計画のとおりに直すか」を 1 つだけ聞く。論点があれば質問に含める。
直すと決まったら、修正計画の手順の順に適用し、手順ごとに関係するテストを流して結果を報告する。

## やらないこと

- バグ探しと性能の指摘。`/code-review` の領分。
- 書式の指摘。lint と formatter に任せる。
- 観点にもリポジトリの規約にも根拠の無い、好みだけの指摘。
- 反証を通していない MUST を報告に載せること。
- ユーザーの判断を待たずにコードを直すこと。
