# テストと Story の観点

1 観点 1 節。各節は 兆候・決まり・直し方の形・重さ (既定)・対象外 で書く。
テストの構造と命名 (Given / When / Then) はリポジトリのテスト規約に従い、ここでは扱わない。

## T-01 決まりを持つファイルには自身のテストを置く

兆候: 2 か所以上から使われる関数・部品 (`git grep` で数える) に自身のテストファイルがなく (`ls` を見る)、呼び出し元のテストを通してしか確かめていない。呼び出し元のテストの中に、その関数の場合分けの表 (色の表・時間帯の 5 つの場合など) が `describe.each` で書かれている。

決まり: 場合分けの表はその関数のテストに移し、呼び出し元には「結果が入ること」を確かめる 1 件だけ残す。呼び出し元のテストが変わってもその関数の決まりが守られる状態にする。

直し方の形は次のとおり。

```text
getRoomColor.test.ts (新規): describe.each(ROOM_COLORS) で 10 色
getReservationDisplay.test.ts: roomColor にこの関数の結果が入る 1 件だけ残す
```

重さ: SHOULD。

対象外: 1 か所からしか使わない見た目だけの部品 (行・チップ・案内) は、親 (表・フォーム) のテストで中身まで確かめてよく、自身のテストがないことは指摘しない。

## T-02 テストは振る舞いを持つ部品のテストファイルに置く

兆候: Container や Root のテストに、子の部品の振る舞い (上限で押せない・ラベルの文言・チップの中身) まで入っている。1 つの部品のテストが膨らんでいる。

決まり: 振る舞いを持つ部品のテストに移す。テストが膨らんでいる部品は責務が広すぎないかも指摘する (structure へ)。ある部品の操作の結果が別の部品に表れる流れは、両方を組み合わせる親の振る舞いとして扱い、移す対象にしない。

重さ: SHOULD。

## T-03 1 つのテストが見る操作と時点は 1 つ

兆候: 初期表示と操作後を同じ `it` で見ている。複数の操作を 1 つの `it` で順に行い、途中の `expect` が混ざっている。

決まり: 1 操作 1 `it`。1 つの操作の結果を複数の `expect` で確かめるのと、1 つの操作の前後で状態が切り替わることを確かめるのは対象外。

重さ: NITS。

## T-04 起こりえない状態と、実装の都合を正しいものとして固めていない

兆候: UI 上できない操作 (押せないボタンを押す) や、起こりえない状態をテストしている。実装の都合 (見つからないメンバーを「通常」として扱う・両方の配列にいないメンバーを落とす) を正しい振る舞いとして固めている。

決まり: 起こりえない状態のテストは消す。実装の都合を固めているテストは、分け方・書き方のレビューの直し方 (判別 union・`undefined` のまま) に合わせて直す対象として挙げる。

直し方の形は次のとおり。

```text
getSelectionRows.test.ts「状況が通常 (status=normal) の行になる」
→「状況が分からない (status=undefined) の行になる」に直す
```

重さ: MUST。

対象外: テストデータの値が実際より広いだけで、結果に影響しないもの。

## T-05 確かめていない振る舞いを列挙する

兆候: 実装の差分で増えた・変わった分岐とユーザー操作の結果のうち、どのテストでも `expect` していないものがある。カバレッジ上は通っているが、ほかのテストの描画でたまたま通っているだけ (例: 時間帯が `null` のとき時間を出さない)。

決まり: 分岐と操作を列挙し、各項目を `expect` しているテストを探す。次を必ず列挙に入れる。

- 応答を待っている間 (ボタン・欄が押せない、Escape で閉じない、もう一度呼ばれない)。応答待ちは、解決を後から呼び出せる Promise を使う
- 失敗したあと (留まる、選んだ値が残る、もう一度できる)
- 応答が返る順番 (複数の API を呼ぶとき、最後が返るまで loading が消えない)
- 守り (`disabled` / Escape で閉じない設定) を外したらそのテストが落ちるか
- ある部品の操作の結果が別の部品の表示に反映される流れ (モーダルでチェックを外して確定すると一覧から外れる・キャンセルすると変わらない) が、親のテストに通しの流れとして書いてあるか
- 開く対象ごとの初期値 (新規・編集・向きを決めずに開く) を、Root を描画して確かめているか
- 保存中に「保存する」を押せないこと (枠の部品のテスト)

アンマウント後の state 更新を防ぐ守り (`isMounted`) は、閉じられる経路が本当にあるときだけテストする。経路がなければ、テストではなく守りを外す側 (expression E-14) に合わせる。

直し方の形は次のとおり。

```text
AssignedRoomChip.test.tsx: Given: 開始・終了時刻とも未入力 (timeRange=null) / Then: 会議室名は出て、時間は出ない
EditModalFrame.test.tsx (新規): Given: 保存中 (isSubmitting=true) / Then:「保存する」を押せない
EditModalRoot.test.tsx (新規): 新規・編集・direction=null の 3 つの初期値
```

重さ: SHOULD。通しの流れと守りは MUST。

## T-06 テストデータとモックは共通のものを使う

兆候: レスポンスの組み立て・応答待ちの Promise・`respondXxx` のような関数をテストファイルの中で書き直している。factory にあるオブジェクトをリテラルで作っている。

決まり: リポジトリの `testing/` 配下の factory と utils を使う (`ls` と `git grep` で確かめる。場所は前例に合わせる)。同じ関数が 2 ファイル以上にあれば共有へ出す。

重さ: SHOULD。

## T-07 この PR で作った・props を変えた部品に Story がある

兆候: 新しい部品、または props が変わった部品に `.stories.tsx` がない (`ls` で確かめる)。同じフォルダに Story の前例がある。

決まり: 見た目だけの部品 (ラベル・チップ・行・表・枠) は、表示が変わる props の組み合わせを Story に出す。例は 0 件・上限と「他 n 件」の境目・長い名前・未入力・時間帯ごと・送信中。store や API につなぐ部品は、MSW で主要な操作を通しで見せる Story を 1 つ置く。

直し方の形は次のとおり。

```text
状況ラベル: 期間外・対象外・欠席
予約チップ: 午前・午後、時間なし、長い会議室名、色ごと
行: チェック済み・押せない・長い名前・チップが多い
表: 0 件・30 名の上限
枠: 送信中
追加・編集モーダル: MSW で「メンバーを追加する」から確定まで
```

重さ: MUST。

対象外: Storybook を入れていないリポジトリ。

## T-08 分けた後に要るテストを列挙する (分け方のレビュー結果があるとき)

兆候: 分け方のレビューが、新しい部品・hook・関数への分け直しを提案している。

決まり: 新しい部品・hook・関数ごとに、確かめる操作と結果を列挙し、いまのテストのどれが移ってくるかを書く。

- hook: hook を呼ぶだけの部品を描画して確かめる。上限のテストは表からここに移る
- ボタンの Root: 押すと取り直してから開くこと、取り直しに失敗しても開くこと、押せない条件
- チップの Root: store とフォームの入力値から、対象の要素だけを出すこと
- 小部品 (チェックボックス): 押すとその ID で `onToggle` が呼ばれること、押せないときは押せないこと
- 型ガード: 各状況と `undefined`
- 枠・並べるだけの部品: Story で見た目を確かめる形で足りる
- Root: フォームの Provider で包んで描画し、確定で入力値が変わることを確かめる

重さ: MUST。
