# polaris-uiux

UI/UX の問題を見つけて Issue にする。コードは直さない。

主セッションは既存のキーを集め、候補を判定し、起票する。
コードを歩いて候補を集めるのは `uiux-auditor` に出す。

## 手順

1. `.claude/skills/polaris-dev/reference/gh-rest.md` と `AGENTS.md` を読む。
2. `.claude/skills/polaris-dev/reference/audit.md` の手順に、`<kind>` = `uiux` で従う。
3. 監査役に渡す観点は `.claude/skills/polaris-uiux/reference/checklist.md`。主セッションはこのファイルを読まなくてよい。

## この監査に固有のこと

- 観点は記事由来の 4 観点だけ。タップ対象の大きさや画面の数など、リポジトリ固有の UI の規則は `CLAUDE.md` の「守ること」にあり、監査役もそちらを優先する。
- ブラウザでの目視はできない。候補はすべて「コードから推した」もので、画面では未確認として扱う。
- 応用問題 (色合い・余白などの細かな調整で、4 観点と目的を損なわないもの) は起票しない。
- 指摘どうしがぶつかるときは、どちらかを選ばず、両方を並べて 1 件の `needs-info` にする。
- データの契約やスキーマを変えないと直せないものは起票しない。報告に「対象外」として理由と一緒に書く。
- 画面や機能を増やす提案は `needs-info` にする。CLAUDE.md が画面の数を決めているときは、それを超える案を出さない。
- 同じ部品・アイコン・文言を使う箇所が他にもあるときは、Issue の「直し方」と「完了の条件」に全箇所を含める。
- Issue 本文の「## 何が起きるか」は、「利用者に起きること (どこで迷う・誤解するか)」の形で書く。続けて、コードから推した再現手順と「画面は未確認」を書く。
