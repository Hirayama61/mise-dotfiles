# リファクタリングの観点とコーディング規約

`refactor-auditor` と `polaris-review` が観点として読む。
項目 ID は監査の重複防止キー (`<ID>:<パス>`) に使う。項目を足すときは番号を詰めない。
書式は lint と formatter に任せ、ここでは扱わない。

## 本人の規約

React + TypeScript の規約。全文と直し方の例は mise-dotfiles の `claude/skills/frontend-review/references/` にあり、ID はそれと同じ。
重さの読み替え: MUST は積 25 (PR を止める)、SHOULD は積 5〜24 (頻度 × 影響で付け直す)、NITS は書かない。
MUST でも、PR が変えていない行にある既存の違反は積 5〜24 として扱い、別 Issue に回す。

### 分け方 (S)

部品は次の 4 層のどれかに置く。

- Root: 取得・フォーム・送信・入れ子モーダルの開閉
- 枠: 配置だけ
- 並べるだけの部品: `ReactNode` の slot で受ける
- 見た目だけの部品: 文字列・boolean・`null` の props

| ID   | 決まり                                                                                               | 兆候・確かめ方                                                                            | 重さ   |
| ---- | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ------ |
| S-01 | モーダルは Root と枠に分ける。親から渡すのは対象と `onClose` / `onCompleted` だけ                    | `Dialog` と取得・フォーム・送信が同居。props が 8 個以上。`renderXxx` で本文を組み立てる  | MUST   |
| S-02 | Dialog の中で Dialog を開かない。Root で兄弟に並べる                                                 | `Dialog` の子孫で別のモーダルを描画している                                               | MUST   |
| S-03 | 並べるだけの部品は `ReactNode` の slot か `children` で受ける                                        | 受け取った props を使わず子へ流している。配列・オブジェクトが素通り                       | MUST   |
| S-04 | 表と行は枠。行の外を見ないと決まらない判定は Root が行う                                             | 表や行が配列を受け取り、行ごとに業務ルールや上限を判定している                            | MUST   |
| S-05 | 見た目だけの部品は API の型を知らない。props は文字列・boolean・`null`                               | `parts/` が API のレスポンス型を丸ごと受け取り中で変換している                            | MUST   |
| S-06 | 1 つの操作の知識は 1 つの部品に。処理はハンドラに置き `useEffect` で起こさない                       | 押せる条件を親が計算し、押した後の取得を子の `useEffect` でしている。`isFetched` の state | MUST   |
| S-07 | Root だけの state のまとまりは `hooks/useXxx.ts` に分ける (boolean 1 つの開閉は除く)                 | Root がチェック状態・上限・確定後の値の state と関数を抱えている                          | MUST   |
| S-08 | 1 機能 1 ファイル。Container は Root を並べるだけ                                                    | 1 つの部品が追加・編集・削除の中身を持つ。行数と props が膨らむ                           | SHOULD |
| S-09 | JSDoc の `@remarks` に持たないことと決める場所を書く                                                 | 分けた部品・関数に「持たないこと」が無い、または実装と合わない                            | NITS   |
| S-10 | 業務ルールは 1 か所でも名前付き純粋関数 (`canXxx` / `isXxx` / `getXxx`) に出しテストを付ける         | 無名の閉包や JSX の中で区分値と `===` 比較している                                        | MUST   |
| S-11 | 関数の入力は役割に要るものだけ。別の用途の値を戻り値に相乗りさせない                                 | 別の表示のための余分な引数。引数がオブジェクト 1 つ                                       | MUST   |
| S-12 | 置き場所は使う範囲で決める。1 か所なら部品のフォルダ、2 か所以上なら共有へ。parts は Root を読まない | `git grep` で使用箇所を数える。1 か所の関数が共有ディレクトリにある、またはその逆         | MUST   |
| S-13 | 同じ型を複数ファイルで書き直さない。元の型から `Pick` / index access で派生させ export する          | `GetXxxResponse["data"][number]` のような別名が複数ファイルにある (`git grep`)            | SHOULD |
| S-14 | 分岐は外側で決める。boolean props で違いを吸収した共通化をしない                                     | 新規と編集・種別の分岐が共通部品の `if` / boolean props にある                            | MUST   |
| S-15 | 同じ役割の部品が隣にあるなら、見た目の決まりは 1 つの枠に寄せる                                      | 同じフォルダの部品が同じ atoms・幅・余白の定数を重複して持つ (`git grep`)                 | SHOULD |

### 書き方 (E)

| ID   | 決まり                                                                                        | 兆候・確かめ方                                                                     | 重さ   |
| ---- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------ |
| E-01 | props は本体の先頭で `const { a } = props;` と分割代入する                                    | 引数の位置で分割代入。`props.xxx` を本文で直接参照                                 | MUST   |
| E-02 | 比較・判定・表記の組み立ては説明変数 (`isXxx` / `hasXxx` / `xxxLabel`) に出してから使う       | JSX や `if` に比較・関数呼び出しがそのまま書かれている                             | MUST   |
| E-03 | 三項演算子でクラス・数・分岐を選ばない。既定クラスと上書きクラス、配列と型ガード、早期 return | `cond ? classes.a : classes.b`。`(x ? 1 : 0) + ...`。入れ子の三項                  | MUST   |
| E-04 | 処理は `filter` → `map` の段階に分け、1 件の変換を関数に出す。1 件探すなら `find`             | `reduce` で絞り込みと変換を同時にしている。長い連鎖が 1 文                         | MUST   |
| E-05 | 未入力・未取得・見つからないは名前付き定数にして比べる                                        | `time ? f(time) : ""`。`x === null` や `?? default` の素の比較                     | SHOULD |
| E-06 | 色・数値は定数。既存の定数を `git grep` してから作り、出どころを JSDoc に書く                 | `"#f5f5f5"` のような直書き                                                         | MUST   |
| E-07 | JSX は並べるだけ。見出しの配列や行の値は変数に出す                                            | JSX の中で配列を組み立てている。`map` の中身が長い                                 | NITS   |
| E-08 | 名前は中身に合わせる。取得 `get` / `find`、変換 `to` / `format`、判定 `is` / `has` / `can`    | 取り出すだけの関数が `to*`。判定が `is*` でない                                    | NITS   |
| E-09 | 作った元が 2 通りある要素は `source` 付きの判別 union にし、元の値をそのまま持つ              | 同じ形に畳んで後段で ID から探し直す。`isXxx: boolean` のフラグで元を表す          | MUST   |
| E-10 | 「分からない」を既定値に畳まない。`undefined` のまま持ち、受け手は出す状況だけの型で受ける    | `x?.status ?? normal`。見た目の部品が `normal` なら `null` を返す                  | MUST   |
| E-11 | 同時に 1 つしか成り立たない状態は `kind` 付き union 1 つの state で持つ                       | boolean の state を並べて段階を表す。段階と一緒に変わる値が別の state              | SHOULD |
| E-12 | 引数は値で並べる。オブジェクト 1 つの引数は責務過多のサインとして関数を分ける (props は除く)  | `fn({ a, b }: XxxParams)`。引数をまとめるだけの型                                  | SHOULD |
| E-13 | `useState` / `useMemo` / `useCallback` で値を固定しない。props から計算できる値は毎回計算     | `useState(() => compute())` で初期値を固定。依存配列から props が抜けている        | MUST   |
| E-14 | `useEffect` を操作の結果や派生値に使わない。`isMounted` は経路があるときだけ                  | 押したことをきっかけにする取得が `useEffect` にある。派生値に `useEffect` と state | MUST   |
| E-15 | `children` は `React.PropsWithChildren<OwnProps>` で受ける                                    | `children: React.ReactNode` を `OwnProps` に書いている                             | NITS   |
| E-16 | 動的な色は `style` に CSS 変数だけを渡し、class 側で `var(--xxx)` を読む                      | `style={{ color, backgroundColor }}` で色を直接当てている                          | SHOULD |
| E-17 | 表に `caption`、アイコンだけの列に見えない見出し、繰り返す対話部品に `aria-label`             | `caption` が無い。見出しが `""`。`fieldset` が要るグループが `div`                 | SHOULD |
| E-18 | ライブラリの標準の書き方を使う                                                                | 共通の表部品にセルの JSX を配列で詰める。配列の並び替えを自前で書く                | SHOULD |

### テストと Story (T)

| ID   | 決まり                                                                                     | 兆候・確かめ方                                                                        | 重さ                             |
| ---- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- | -------------------------------- |
| T-01 | 2 か所以上で使う関数・部品には自身のテスト。場合分けの表はそこに移す                       | `git grep` で使用箇所、`ls` でテストファイルの有無。呼び出し元に `describe.each` の表 | SHOULD                           |
| T-02 | テストは振る舞いを持つ部品のファイルに置く                                                 | Root のテストに子の振る舞い (押せない・文言) まで入っている                           | SHOULD                           |
| T-03 | 1 操作 1 `it`                                                                              | 初期表示と操作後を同じ `it` で見ている                                                | NITS                             |
| T-04 | 起こりえない状態と実装の都合を正しいものとして固めない                                     | 押せないボタンを押すテスト。見つからない値を既定値に畳む振る舞いを固定                | MUST                             |
| T-05 | 確かめていない振る舞いを列挙する (応答待ち・失敗後・応答順・守り・通しの流れ・初期値)      | 分岐と操作を列挙し、`expect` しているテストをテスト本文で探す                         | SHOULD (通しの流れと守りは MUST) |
| T-06 | テストデータとモックは既存の factory / utils を使う                                        | テストファイル内で補助関数を書き直している。factory にある形をリテラルで作る          | SHOULD                           |
| T-07 | 新しく作った・props を変えた部品に Story を置く (Storybook のあるリポジトリ)               | `ls` で `.stories.tsx` の有無。同じフォルダに Story の前例がある                      | MUST                             |
| T-08 | 分け直しの提案があれば、新しい部品・hook・関数ごとに要るテストと移ってくるテストを列挙する | 分け方の指摘に「移るテスト」が無い                                                    | MUST                             |

## リファクタリング監査の追加観点

外から見た振る舞いを変えずに、次に触る人 (主に開発係) が壊しにくく、直しやすくなるものだけを扱う。

| ID  | 観点                                                                                            | 確かめ方                            |
| --- | ----------------------------------------------------------------------------------------------- | ----------------------------------- |
| R01 | 重複。同じ処理が 2 か所以上にあり、片方だけ直すと食い違う                                       | `git grep` で似た式や同じ定数を探す |
| R02 | 長い関数・コンポーネント。1 つが複数の責務 (取得、整形、描画、保存) を持ち、50 行を大きく超える | 関数の行数、hook と描画の混在       |
| R03 | 不要な export。どこからも import されていない export                                            | `git grep` で import 元を数える     |
| R04 | 死んだコード。呼ばれない関数、到達しない分岐、使われない CSS クラス                             | 呼び出し元とクラス名の Grep         |
| R05 | テストの無い純粋関数。入力と出力だけで決まる関数に `*.test.*` が無い                            | 関数の所在と同名のテストファイル    |
| R06 | 命名の揺れ。同じものを指す名前が場所によって違う (例: daily と today、task と todo)             | 型名・変数名・関数名の Grep         |
| R07 | props のバケツリレー。中間のコンポーネントが使わない props を 2 段以上受け渡している            | props の定義と使用箇所              |
| R08 | 副作用の混入。純粋にできる計算が、fetch や localStorage の読み書きと同じ関数にある              | 純粋関数の中の I/O                  |
